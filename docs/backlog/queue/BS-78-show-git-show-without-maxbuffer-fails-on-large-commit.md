# BS-78 · show N падает с ENOBUFS: git show <rev> целиком без maxBuffer, а коммит приёмки массовой свёртки весит 6,3 МБ

- **Порядок:** 200
- **Область:** [02. Команды](../../reference/02-cli.md) § `show`
- **Создана:** 2026-09-23
- **Цена:** major
- **Зависимости:** нет

## Контекст

Приёмка BL-708 у потребителя ati-agents (2026-09-23): строка журнала BL-708 несёт ревизию `—` (тело в сообщении коммита приёмки), и `show 708` ищет коммит по заголовку `BL-708:` и зовёт `git show <rev>` целиком — с диффом. Коммит приёмки массовой свёртки удаляет ~1550 файлов архива и весит 6,3 МБ, буфер `spawnSync` по умолчанию (1 МБ) переполняется: `show 708` → код 1, `ENOBUFS`. Тело при этом читается штатно: `git show -s --format=%B 87f0b48f` — 9136 байт, `task.md` и `result.md` внутри. Дефект в `lib/show.js`: для строки с `—` нужно только сообщение коммита, а команда читает и дифф; `maxBuffer` не задан. Тот же обрыв ждёт любой крупный коммит приёмки (перепин с массовой переписью ссылок, свёртка пачки).

## Что сделать

- `lib/show.js`: для тела из сообщения коммита звать `git show -s --format=%B <rev>` (или `git log -1 --format=%B`), без диффа; для тела из файлов — по-прежнему `git show <rev>:<путь>` пофайлово.
- Всем вызовам `git` в `lib/`, чей вывод может расти с размером репозитория (`show`, `fold`, `lint` гейт 13 `rev-list`), задать `maxBuffer` явно (например 64 МБ) — и назвать предел в справочнике 02.
- Справочник 02 § `show`: откуда читается тело для `—` и для ревизии; CHANGELOG.

## Не входит

- Формат заготовки и что попадает в сообщение коммита (BS-74, BS-77).
- Перегенерация журналов у потребителей.

## Проверки

- `test/commands.test.mjs`: репозиторий, где коммит приёмки несёт тело в сообщении и дифф больше 1 МБ (например, удалённый файл в 2 МБ) → `show N` код 0, печатает `task.md` и `result.md` из сообщения; до правки — код 1 с `ENOBUFS` (красная проба).
- Мутационная проба: вернуть `git show <rev>` без `-s` → вердикт краснеет; код и счёт в `result.md`.
- `node bin/backslop.js gates` → «гейтов 2, зелёных 2».
