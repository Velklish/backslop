# BS-108 · Remove pre-0.9.0 version gates: GATES_SINCE, 0.9.0 migration, MIN_UPGRADE_TARGET, Area

- **Order:** 260
- **Scope:** [02. CLI](../../reference/02-cli.md) § upgrade
- **Created:** 2026-09-25
- **Dependencies:** BS-104, BS-90

## Context

All evidence below was taken at commit 6f6318e (v0.11.0), where `npm test` runs 450 tests (450 pass, rc=0) and `node bin/backslop.js lint` exits 0. "Removal probe" means: the change was applied in a throwaway clone at that commit, then the full suite and lint were run.

Support floor: no consumer runs a version below 0.9.0, so code that only serves older pins, stamps or task files is dead code. Four such branches remain.

- **brief: the fallback for pins without a `gates` runner.** The BS-90 (`brief-follows-cli-pin`) card added a pin check for the brief's `--evidence` command; keep it. verified — history, a live repro and a removal probe. lib/brief.js:14 is `GATES_SINCE = '0.5.0'`; `pinHasGates` at :117-120 returns `!form || form.pin === null || compareVersions(form.pin, GATES_SINCE) >= 0`, and the fallback text sits at :143-146. `gates` first ships in v0.5.0 (`git show v0.4.0:lib/gates.js` gives rc=128, `git show v0.5.0:lib/gates.js` gives rc=0), and upgrade refuses downgrades (lib/upgrade.js:121-122), so a pin of 0.9.0 or later reaches the fallback only through a hand edit. Live: with the cli pin edited to `#v0.9.0`, `brief 1` prints the runner paragraph ('печатает итог «гейтов N, зелёных N»'); with `#v0.4.0` it prints 'Раннера `gates` в пинованной версии нет (команда появилась в v0.5.0)'. Removal probe: deleting GATES_SINCE, pinHasGates, the fallback, the now-unused `parseCli` (:3) and `compareVersions` (:9) imports, and the stale-pin half of test/brief.test.mjs:179-187 kept 450/450 and lint rc=0. The comment at test/brief.test.mjs:174 says pin 1.2.3 is "старше v0.5.0" (older than v0.5.0), but it is newer. docs/reference/02-cli.md:19 still describes the fallback.
- **migrate: the `since: '0.9.0'` entry (create docs/backlog/minor/.gitkeep).** verified — history, a live check and a removal probe. The due filter at lib/migrate.js:79 is `MIGRATIONS.filter((m) => from === null || compareVersions(from, m.since) < 0)`, so the entry at :17-26 never runs for a stamp of 0.9.0 or later. The minor status and this migration arrived in the same commit, first tagged v0.9.0. init already creates `.gitkeep` for every status, including minor (lib/init.js:145-150), and upgrade always runs `migrate` and then `init` (lib/upgrade.js:162-163). Live: in a fresh project, `rm -rf docs/backlog/minor; node <repo>/bin/backslop.js init; echo rc=$?` gives rc=0, and docs/backlog/minor/.gitkeep is back. Removal probe: `npm test` gave rc=1 with 450 tests, 447 pass and 3 fail: 'migrate до v0.9.0 создаёт каталог minor/ в проекте со старым штампом' (test/commands.test.mjs:1242), 'release-related CLI messages follow project lang without changing their flow' (test/commands.test.mjs:630/636) and 'upgrade без источника релизов отказывает; migrate и changelog в одиночку' (test/upgrade.test.mjs:213/223). Lint stayed at rc=0. The only change in behaviour: an unstamped project that lacks minor/ and runs `migrate` alone gets a lint error about the missing directory until it runs `init`, which the documented `migrate` then `init` flow always does. docs/reference/02-cli.md:26 lists this migration.
- **upgrade: `MIN_UPGRADE_TARGET = '0.2.0'`.** verified — a live probe and a removal probe. lib/upgrade.js:11-13 holds the comment and `export const MIN_UPGRADE_TARGET = '0.2.0';`, and the guard at :116-118 refuses with 'v${target} старше v0.2.0: у таких версий нет migrate и upgrade…'. The downgrade refusal at :120-123 (`current = form?.pin ?? cfg.version ?? null`) already covers every project that has a pin or a stamp. init has written the stamp since v0.2.0, so every project init'd at 0.9.0 or later has one. The export has no consumer (`grep -rnw MIN_UPGRADE_TARGET lib bin scripts test templates docs` finds only lib/upgrade.js:13, :116 and :117). The guard is still reachable for a hand-edited config with neither a pin nor a stamp, because `version` is optional in loadConfig (lib/config.js:129) and `npx github:owner/repo` without `#v` has no pin. With such a config, the base refuses `upgrade --to v0.1.0` with rc=1, while the patched clone plans the upgrade with rc=0. Removal also turns test/upgrade.test.mjs:176 red: it asserts `/старше v0\.2\.0/` on a fixture pinned at v0.2.0, and after removal that case gets the downgrade message instead ('понижение v0.2.0 → v0.1.0 не поддерживается'). Owner decision: targets below the 0.9.0 floor are not supported, so the guard goes and the pinless, stampless edge is accepted. docs/reference/02-cli.md:25 and :39 still mention the refusal ('цель старше 0.2.0').
- **tasks: the header-field alias `Area`.** verified — a grep over every tag and a removal probe; it is dead for every release, not just under the floor. lib/tasks.js:30 is `area: { ru: 'Область', en: 'Scope', compatibility: 'Area' }`, and `fieldAliases` (:54-57) accepts every value as a field name. `for t in $(git tag); do git grep -n -e '\*\*Area' $t -- templates lib | wc -l; done` prints 0 for all 13 tags. The alias was added together with the English layer, whose templates always emitted `- **Scope:**`. `grep -rn -e compatibility -e "'Area'" -e 'Area:' lib bin test templates docs scripts` finds only lib/tasks.js:30 and docs/reference/01-layout.md:66 (`- **Область / Scope / Area:**`). No test covers it, and removing it kept 450/450 and lint rc=0.

- ADRs: do not edit docs/adr/ here. The BS-146 (`adr-worker-brief`) and BS-152 (`adr-pin-upgrade-migrate`) cards record the code without any pre-0.9.0 branch.

It should say that support for pins and stamps below 0.9.0 is removed: `brief` no longer has a fallback for pins without the `gates` runner, `migrate` no longer creates `docs/backlog/minor/` for pre-0.9.0 stamps (`init` still does), `upgrade` no longer has a separate refusal for targets below 0.2.0, and the `Area` header alias is gone.

## Out of scope

- Introducing a new floor constant or refusing targets below 0.9.0; that would be a feature, not a removal.
- The `since: '0.10.0'` migration.
- Legacy adapter ownership and the `tools` inference; the BS-107 (`marker-only-adapter-ownership`) card handles those.
- Other legacy fallbacks in lib/log.js (reading old result headings) that are not listed here.
