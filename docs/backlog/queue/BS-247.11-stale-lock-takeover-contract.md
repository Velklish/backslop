# BS-247.11 · Align stale-lock instructions and refusal text with identity-checked takeover

- **Order:** 90
- **Scope:** [01. Layout and formats](../../reference/01-layout.md)

- **Dependencies:** none

## Context

Evidence: `docs/reference/01-layout.md:194-194` at source `44e74a32ff6a6b6c946321b3614b1881a2ccedfe`; the source snapshot and recorded checks below establish the audit claim. Follow the repository verification protocol before implementation.

The allocator recovers an old numbering lock by claiming its observed identity, rechecking it and atomically replacing the lock path. Several current instructions still tell readers that the next `new` removes a stale lock. This is a documentation and diagnostic-text contradiction, not a demonstrated failure of the locking algorithm.

Evidence was inspected at source HEAD `44e74a32ff6a6b6c946321b3614b1881a2ccedfe`. The audit baseline at that HEAD was gates 2/2 and tests 1240/1240, exit 0; that is not verification of a future fix.

## Evidence

- `docs/reference/01-layout.md:194`: a lock older than 60 seconds "is stale: the next `new` removes it and goes on". The same page at `:200` says "A stale lock is never removed" and describes claim/rename.
- `docs/reference/02-cli.md:95` and `docs/backlog/README.md:27` repeat removal language; the latter says "is stale and is removed". The backlog rule is supplied by `templates/en/docs/backlog/README.md` and `templates/docs/backlog/README.md`.
- `lib/lock.js:89-110` reads content/stat, acquires the identity-derived claim, rechecks the lock, writes its own file and calls `rename(own, lock)`. Release at `:118-120` deletes the path only when the stored token is still its own.
- `lib/lock.js:134` includes the user-facing fragment "a lock older than {stale} s is removed by the next `new` on its own". The EN key and RU translation are paired at `templates/i18n/ru.mjs:359`, and `test/new-lock.test.mjs:15` pins this REFUSAL text.

The stale prose survived a change in recovery mechanism. It presents two incompatible models and could cause a caller to copy an unsafe unlink-then-create sequence.

## Work to do

1. Describe waiting and takeover separately: an old lock can be taken over after its identity is rechecked, without leaving the lock path free. Update both reference pages, EN/RU backlog template twins and their rendered `docs/backlog/README.md` together.
2. Align the refusal in `lib/lock.js`, its EN/RU message-key pair and the exact REFUSAL assertion. Preserve placeholders and the conditional manual-removal advice that applies only when no live process remains.
3. Update only affected live quotes/guards in `docs/README.md`. Search current instructions for equivalent removal claims; leave accurate historical CHANGELOG descriptions alone.
4. Make the focused assertion distinguish the old erroneous takeover statement from the corrected contract. Keep the existing ownership and recovery coverage.

Acceptance: all normative descriptions and refusal text agree with `recover`; template/render parity and EN/RU message pairing hold; no instruction prescribes unlink before takeover.

## Out of scope

Do not change the lock algorithm, exit behavior, 10-second wait, 60-second stale threshold, token ownership or claim protocol. Preserve ADR-050's explicit limit for a holder or claimant suspended for too long; the wording must not promise an unlimited lock guarantee. Manual removal when no live process exists is a different operation and remains available.
