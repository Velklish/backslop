# BS-26 · mv принимает один номер задачи за вызов, поэтому перевод track'а из пяти задач в работу стоит пяти вызовов и пяти аппрувов

- **Порядок:** 130
- **Область:** [reference/02](../../reference/02-cli.md), `lib/mv.js`, `bin/backslop.js`
- **Создана:** 2026-09-06
- **Зависимости:** нет
- **Слито сюда:** BS-30 в части пакетного `mv` (остаток BS-30 — сохранение ранга — отложен)

## Контекст

Проверено сегодня на v0.4.0: lib/mv.js:23 — `const [rawId, target] = positionals;` — команда читает ровно один номер, лишний позиционный аргумент уходит в target. Живой прогон в подставном проекте: `new task-a --queue; new task-b --queue; new task-c --queue; mv 1 2 3 active` → «✖ статус «2» неизвестен; есть triage, queue, active, deferred. Закрытие — backslop archive», код 1. docs/reference/02-cli.md:13 и `backslop help` подтверждают форму `mv <N> <статус> [--top | --after M]` — второго номера в контракте нет.

Место в очереди при уходе из queue/ не сохраняется: lib/mv.js:61 — `else text = removeField(text, FIELD_ORDER)` — поле «Порядок» снимается целиком, не запоминается. ADR-002 (Consequences) называет «Порядок» абсолютным целым, которое очередь перенумеровывает шагом 10, когда целого места нет, — то есть даже сохранённое число не гарантированно означает то же место после следующего захода.

Оркестратор вызывает mv N active на каждую розданную задачу — .claude/skills/backslop-batch/SKILL.md:33 («переведи розданные задачи в работу: `backslop mv N active` на каждую») и .claude/skills/backlog-batch/SKILL.md:43 (аналогично); источник обеих формулировок — templates/skills/backslop-batch/SKILL.md:32 и templates/en/skills/backslop-batch/SKILL.md:32. Масштаб называет архивная BS-10: «Наблюдение оркестратора 2026-09-05 в external/promptobus (15 track'ов, 33 задачи)» — тот же заход, где mv вызывался по разу на задачу.

## Что сделать

- backslop mv <N…> <статус> [--top | --after M] — несколько номеров в одном вызове. Все номера резолвятся и проверяются до первого переноса (задача существует, не в архиве, не в целевом статусе уже без флага положения) — тем же принципом, что и текущее «место в очереди mv считает до переноса» (docs/reference/02-cli.md:23): отказ не должен оставлять часть номеров перенесённой, а часть нет.
- Перенос — по одному номеру в порядке аргументов; вывод — строка ok на каждый плюс одна сводка перенумерации очереди (как сейчас после new --queue).
- -top / --after при нескольких номерах — отказ: место для пакета не определено одним числом.
- Семантика отказа — «всё или ничего», как записано выше: слитая BS-30 предлагала обратное (применять по кругу и не прерываться на первом отказе, печатая сводку по каждому номеру). Взят атомарный вариант: он повторяет уже задокументированное поведение самой команды («место в очереди mv считает до переноса», docs/reference/02-cli.md:23), а половина перенесённого пакета оставляет оркестратора без понятного состояния каталогов.
- Правки: lib/mv.js, help в bin/backslop.js, docs/reference/02-cli.md (строка контракта mv), README.md / README.ru.md, шаблоны docs/backlog/README.md (ru/en), строка шага в templates/skills/backslop-batch/SKILL.md и templates/en/…, CHANGELOG.md.
- test/commands.test.mjs: пакет из нескольких номеров переезжает в active одним вызовом; отказ по несуществующему номеру в пакете не двигает ни один файл; --top с двумя номерами — отказ.

## Не входит

- Сохранение прежнего «Порядка» отдельным полем при выходе из очереди: ранг — абсолютное целое, которое сама очередь перенумеровывает шагом 10 (ADR-002, Consequences), так что через заход сохранённое число уже не значит того же места; новое поле шапки по ADR-002 тянет за собой lint, migrate и весь комплект справочников — ради приоритета, который оркестратор при возврате назначает заново (--top для незакрытой работы).
- Изменение самой логики placeInQueue и перенумерации шагом 10 — она уже пакетная, эта задача её не трогает.
