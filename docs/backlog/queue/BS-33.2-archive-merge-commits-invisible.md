# BS-33.2 · Merge-коммиты не попадают в список тронутых доков `archive`

- **Порядок:** 20
- **Область:** `lib/archive.js`, `test/commands.test.mjs`, [02-cli](../../reference/02-cli.md)
- **Создана:** 2026-09-09
- **Зависимости:** нет

## Контекст

Находка при работе над BS-33.

`touchedDocs` (`lib/archive.js`) собирает файлы через `git log --format=%x01%s --name-only`. Предположение по документации git, отдельным прогоном не замеряно: `git log --name-only` для merge-коммита диффа не печатает вовсе (нужен `-m`, `--first-parent` или `-c`/`--cc`). Значит файл документации, попавший в ход задачи только через merge, в списке не окажется — approver увидит неполный список и решит, что доку не трогали.

Для самого backslop это сегодня безразлично: работа идёт прямо в `main` без веток и MR (`AGENTS.md`, раздел «Фаза разработки»), merge-коммитов в истории задач нет. У потребителя с ветками и MR — иначе, а `archive` пишется как инструмент для потребителей.

## Что сделать

- Замерить: репозиторий с веткой, менявшей `docs/**`, и merge-коммитом в `main`; `archive N --range <база>..HEAD` — попадает ли файл в список.
- Если предположение подтвердилось — выбрать поведение (`--first-parent` при разборе диапазона либо `-m` со схлопыванием дублей) и назвать его в `docs/reference/02-cli.md` строкой про `archive`.

## Не входит

- Разбор истории merge'ей по существу и выбор стратегии слияния проекта — здесь только полнота списка, который печатает команда.

## Проверки

- Тест на репозитории с merge-коммитом: файл, изменённый только в ветке, назван в списке тронутых доков.
