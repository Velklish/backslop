The mechanism as implemented.** verified — `node --test --test-name-pattern='restore|Прежний порядок|место в очереди|тесной очереди|перенумер|очередь → работа|пакет номеров' test/tasks.test.mjs test/commands.test.mjs test/lint.test.mjs; echo rc=$?` -> tests 18, pass 18, `rc=0`; the ADR counterexample through the CLI (en project, queue BS-5 Order 7, BS-6 Order 12; Previous order BS-1 13, BS-2 10, BS-3 8, BS-4 13): `node <repo>/bin/backslop.js mv 1 2 3 4 queue --restore` -> `BS-4 “Order” 13 restored`, `BS-1 saved position 13 is taken — “Order” 30`, `BS-2 saved position 10 is taken — “Order” 5`, `BS-3 saved position 8 falls behind BS-2 from the same batch — “Order” 2, ahead of it`, `queue renumbered in steps of 10: 3 files`, final BS-3 2, BS-2 5, BS-5 10, BS-6 20, BS-1 30, BS-4 40, rc=0, lint rc=0; the permutation check of test/tasks.test.mjs:143 over 100 000 configurations -> 0 inversions with the bound, 14 310 without it.
- Order (`Порядок`, lib/tasks.js:28) is an integer, lower first; ties by task number then sub-number; a missing or non-integer Order sorts last and is not renumbered (lib/tasks.js:495-501, :511). Only `queue/` tasks carry it: `mv` writes it on entering `queue/` and removes it for any other target (lib/mv.js:148-149).
- Placement (`placeInQueue`, lib/tasks.js:510-568): no position -> max integer Order + 10, or 10 on an empty queue (:503-506); `--top` -> midpoint between 0 and the first Order; `--after M` -> midpoint between M and the next, or M + 10 at the tail; M must be a queue task with an integer Order (:533-544); midpoint = floor((lower + upper) / 2) when the gap is at least 2 (:550), otherwise every integer-ranked queue task is renumbered 10, 20, … (:551-567) and the command prints `queue renumbered in steps of 10: N files`, counting distinct files per call (lib/mv.js:243, :252, :256).
- Entry points: `new <slug> --queue [--top]` (lib/new.js:129); `mv <N…> queue` without a flag appends each task to the tail in argument order; `mv N queue --top | --after M`; `mv <N…> queue --restore`. A task already in `queue/` is reordered in place and needs a position flag (lib/mv.js:93-95). `--top`, `--after`, `--restore` are mutually exclusive and valid only with target `queue`; `--top`/`--after` take one task, `--restore` a batch (lib/mv.js:212-218).
- Saved rank: leaving `queue/` writes an integer Order into Previous order (`Прежний порядок`, lib/tasks.js:29; lib/mv.js:144-147); a non-integer Order saves nothing; the field survives moves between other statuses and is removed on every entry into `queue/` (lib/mv.js:146); a duplicated line (ru/en aliases included) is a gate-4 error (lib/lint.js:335-342).
- `--restore` reads Previous order of every named task before the first move and refuses the whole call, naming every offender, if any is missing or non-integer (`restoreRanks`, lib/mv.js:101-116, called at :236). A free saved rank is taken exactly for a single task; a taken one places the task right before the occupant (lib/tasks.js:517-528).
- Batch guarantee: restored tasks end in ascending saved rank, ties by ascending task number, whatever the argument order. The batch is processed by descending saved rank, then number and sub-number (lib/mv.js:239); the queue is re-read before each move (lib/mv.js:123); every task after the first is bounded by the batch task placed just before it — a free saved rank greater than that neighbour's Order, or one taken by a task behind the neighbour, goes right before the neighbour and `placeInQueue` answers `bounded: true` (lib/tasks.js:523-525). Per-task lines report the rank at placement time; a later step of the same batch may renumber it, which only the summary line shows (lib/mv.js:175-177, :248-256).
- Entering `queue/` without `--restore` discards Previous order and prints `<ID>: saved position N discarded — --restore would have put it back` only when the saved value is an integer; a non-integer one is removed silently (lib/mv.js:145-146, :178).

## Work to do

- Create the ADR (`node bin/backslop.js adr queue-order --title "Queue order: an integer rank per file, a saved rank on leaving, restore by batch"`). Context: priority must be editable on parallel branches without a shared file; each queued task carries its own absolute rank; a task that leaves the queue loses its place unless the rank is saved, and a saved number is a place, not an identical position, because the queue may be renumbered meanwhile; an orchestrator returns a whole track at once, so restore takes a batch and must not invert it. Options: a shared ORDER/index file (conflicts on every take and reorder); order by task number (cannot express priority); restoring the exact number (impossible after renumbering). Decision: item 1. Consequences: branches conflict when they move the same task, when a move rewrites a file another branch edits (incoming links) or when both renumber the queue; seeing the queue costs a command (`status`, `status --json`); `--restore` returns a place, and within a batch a task with a free number may land ahead of it; tasks without Previous order cannot be restored and get `--top` or `--after M`; the `mv` output lines and the field names are part of the CLI and layout contract; lint checks Order and Previous order only as in item 2 and `mv` keeps the rest consistent.
