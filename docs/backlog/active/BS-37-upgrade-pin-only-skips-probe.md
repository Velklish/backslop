# BS-37 · `upgrade --pin-only` переставляет пин и `gates` без пробного запуска новой версии — `lint` после этого зелёный, а без ручной правки `backslop.json` проект не поднимает собственный CLI

- **Область:** `lib/upgrade.js`, [reference/02](../../reference/02-cli.md)
- **Создана:** 2026-09-06
- **Зависимости:** нет
- **Взята:** 2026-09-09

## Контекст

`lib/upgrade.js:108` — `if (!pinOnly) exec(`${newCli} version`, root, recovery, cfg.lang);`, а запись пина и гейтов идёт следом безусловно (110-114: `cfg.cli = newCli; cfg.gates = newGates; saveConfig(root, cfg);`). Шапка того же файла (4-5) объявляет обратный инвариант без оговорок: «Пин записывается только после того, как новая версия хоть раз запустилась: иначе отказ сети или тега оставлял бы проект с пином на версию, которой нет». `docs/reference/02-cli.md:18`, колонка отказов `upgrade`: «ls-remote или пробный запуск отказали — пин не тронут» — тоже без оговорки про `--pin-only`.

Тесты зелёные и опираются на пропуск: `npm test` — 134/134. `test/upgrade.test.mjs:66-77` берёт `cli: 'npx --yes -q backslop@0.2.0'` без исполняемого источника такой версии, гоняет `upgrade --pin-only` и получает код 0 с записанным `cli: 'npx --yes -q backslop@0.3.0'`; тест на `--dry-run`/`--pin-only` (`test/upgrade.test.mjs:108-125`) — то же на GitHub-форме `npx github:me/proj#v0.1.0`, репозитория `me/proj` не существует. `lint` после `--pin-only` только предупреждает «пин в cli v0.2.0 расходится со штампом v0.1.0» (`lib/lint.js:66`) — исполнимость `cli` он не проверяет; `gates` при этом переписаны теми же строками, что и `cli`.

Пропуск не выглядит осознанным выбором: ветка `!pinOnly` и проба на неё пришли одним коммитом (BS-4), а `docs/archive/BS-4-upgrade-and-pin/result.md` называет пробный запуск до пина условием приёмки: «мутационная проба… снят пробный запуск до пина — красные 2 из 10». Ни ADR-004, ни ADR-007 пропуск пробы при `--pin-only` не оговаривают. Итог сценария: `cli` и переписанные `gates` указывают на команду, которая не запускается, а лечение — правка `backslop.json` руками, потому что сам `backslop` из проекта больше не поднимается.

## Что сделать

- Развилка для владельца, не для решения агентом: Вариант A — проба идёт и при `--pin-only`: убрать условие на `lib/upgrade.js:108`, флаг сокращает только хвост (`migrate`, `init`, выжимка CHANGELOG); тогда правятся оба теста, опирающихся на пропуск (`test/upgrade.test.mjs:66-77` и `108-125`) — им нужен доступный источник поставки (шим в PATH, как в тесте «пробный запуск до пина»).
- Вариант B — пропуск остаётся, но объявлен: оговорить его в шапке `lib/upgrade.js:4-5`, в колонке отказов `docs/reference/02-cli.md:18`, в `help` и в обоих README, и добавить `warn` при записи пина без пробы.
- Для варианта A — тест: `--pin-only` с недостижимой новой командой (несуществующий источник) не меняет `backslop.json`. Для варианта B — тест не нужен, `warn` проверяется по выводу существующих тестов на `--pin-only`.

## Не входит

- Смена формы зависимости (npm вместо git-пина) или другой механизм самого пина — этой развилки не касается.
- Автоматическое восстановление проекта после отказа (откат пина и т. п.) — вне зависимости от выбранного варианта это правка владельца конфигурации руками.

## Проверки

- Вариант A: красная проба «`--pin-only` с недостижимым source не пишет пин» становится зелёной; `npm test` зелёный.
- Вариант B: `docs/reference/02-cli.md`, `help` и README называют пропуск пробы явно; `upgrade --pin-only` печатает предупреждение о непроверенной команде.
