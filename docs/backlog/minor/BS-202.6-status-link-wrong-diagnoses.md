# BS-202.6 · Two narrow wrong diagnoses for a status directory link: a locked project directory and a link through a symlinked path prefix

- **Scope:** [Reference index](../../reference/README.md)
- **Created:** 2026-10-02
- **Parent:** BS-202
- **Cost:** minor

## Evidence

Finding discovered while working on BS-202.

Evidence: Measured on the BS-202 branch. (a) docs/locked (mode 000) holds tasks/ inside the project, docs/backlog/queue is a symlink to the absolute real path of docs/locked/tasks -> 'status' rc 1 '✖ docs/backlog: the directory is not readable (EACCES)': the link is judged inside the project, then isDirectory in lib/tasks.js fails and the walk for the denying ancestor stops at docs/backlog instead of docs/locked. (b) the project lives under a symlinked prefix (macOS: mktemp -d gives /var/folders/..., real path /private/var/folders/...); docs/backlog/queue is a dangling absolute symlink to <project>/docs/nowhere written with the /var spelling -> 'status' rc 0 with the warning 'docs/backlog/queue: a symlink leading out of the project': leadsOut in lib/tasks.js resolves the link text against the real root and the unresolved /var spelling never matches, so a dangling link inside the project is judged out. Both cases are narrow: (a) needs a link under a locked project directory, (b) a dangling absolute link through a symlinked prefix.
