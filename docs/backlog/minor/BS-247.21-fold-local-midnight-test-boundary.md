# BS-247.21 · Verify and bound the local-midnight date race in the fold journal test

- **Scope:** [04. Finding verification protocol](../../reference/04-verification.md)
- **Created:** 2026-10-22
- **Parent:** BS-247
- **Cost:** minor (hypothesis)

## Context

A fold integration test computes its expected fallback date after the child command returns. If the child's journal write and the parent's expectation straddle local midnight, the test can reject a valid journal line. This is a static hypothesis: no real midnight failure, stress reproduction or clock-injection proof was obtained in the audit.

Evidence was inspected at source HEAD `44e74a32ff6a6b6c946321b3614b1881a2ccedfe`. The relevant boundary is the machine's local calendar day and inherited time zone, not UTC.

## Evidence

- `test/fold.test.mjs:811-813` runs `const rest = cli(root, ['fold']);`, asserts exit 0 and then matches the line's date against a new parent-side `today()` value, with the assertion explanation "without a revision — the fold day".
- `lib/fold.js:243` obtains the fallback date with `today()`. `lib/util.js:25-28` uses `new Date()` with `getFullYear`, `getMonth` and `getDate`.
- `docs/reference/05-orchestrator-contract.md:17` defines the machine calendar date in its own time zone. `test/helpers.mjs:70-72` passes the inherited environment to the child; this invocation does not set an independent `TZ`.
- A child can write day D just before midnight while the parent resumes on D+1. File concurrency and timeout in `package.json:18` do not prevent this calendar boundary.

## Work to do

1. Establish the boundary with an isolated bounded clock/scheduling probe: a correct child journal line on D followed by a parent post-check on D+1 should expose the old expectation mismatch. Record the result; until then retain hypothesis status.
2. If confirmed, capture `today()` before and after the CLI invocation, parse the journal date separately and accept either boundary date. Preserve the separate anchor, outcome and revision-semantics assertions.
3. Prefer that narrow test-only change. Use control of both processes' clocks only if the project already supplies an appropriate mechanism; do not introduce a production clock abstraction for this one test.

Acceptance: correct D is accepted when the parent checks on D+1; a date outside the invocation's before/after dates still fails, as do a wrong anchor, wrong outcome or changed revision semantics. An ordinary non-boundary run remains meaningful. Document the local time zone used by the boundary proof.

## Out of scope

Do not change production date semantics, hard-code UTC, weaken the entire line assertion, declare a measured load-flake frequency, or claim an actual failure before the boundary probe reproduces it.
