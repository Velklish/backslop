# 02. CLI и контракт для оркестратора

Точка входа — [bin/backslop.js](../../bin/backslop.js): первый аргумент — команда, модуль `lib/<команда>.js` экспортирует `run(argv, { cwd })`. Отказ, адресованный человеку, — `CliError`: печатается без стека, код возврата 1. Любое другое исключение — ошибка кода, со стеком. Вывод: `✔` — успех, `✖` — ошибка, `⚠` — предупреждение; цвет только на терминале.

Флаги разбирает `parseArgs` в строгом режиме через `parseCommandArgs` ([lib/util.js](../../lib/util.js)). Значение строкового флага, начинающееся с дефиса, принимается и через пробел (`--title "--strategy …"`): пара склеивается в `--title=…`, если значение не совпадает с именем флага этой команды; `--title --queue` — отказ с подсказкой формы `--title=…`, надёжная форма для любого значения — с «=». Справка называет это правило.

## Команды

| Команда | Что делает | Отказ (код 1) |
|---|---|---|
| `init [--dir docs] [--prefix BS] [--cli <команда>] [--lang ru\|en] [--tools <CSV\|none>]` | раскладка скелета; ADR процесса — `adr-001-process.md`, а в проекте со своими ADR — следующий свободный номер; см. [01](01-layout.md) | флаг `dir`/`prefix`/`cli` расходится с существующим конфигом; неизвестный `lang` или `tools`; проект инициализирован выше; symlink на корне выбранного adapter'а (до первой записи; корни невыбранных не проверяются); каталог на пути adapter output или файл на компоненте его пути; штамп новее инструмента; плохой префикс или путь |
| `new <slug> [--title "…"] [--queue [--top]] [--parent N[.M]]` | файл задачи из шаблона в `triage/`, с `--queue` — в очередь с порядком в конец или сверху; `--parent N` — находка `N.k`; `--parent N.M` — находка под находкой, следующий свободный `N.k` и поле «Родитель» с точным номером родителя. Для находки `new` печатает поле «Улика»/`Evidence` отдельной строкой с заглушкой, которую нужно заполнить; «Область» подставляется ссылкой на `reference/README.md` с уже посчитанной от каталога статуса глубиной (в проекте без этого файла — текстом); раздел справочника выбирает и дописывает тот, кто заводит задачу. Номер — следующий свободный по текущему дереву, другим worktree и локальным веткам ([01](01-layout.md)); чужой занятый номер называется в выводе | плохой slug; родителя нет; `--top` без `--queue` |
| `mv <N…> <triage\|queue\|active\|deferred> [--top \| --after M]` | `git mv` между каталогами; номеров может быть несколько за вызов — все резолвятся и проверяются до первого переноса, дальше перенос по одному в порядке аргументов, строка ok на каждый и одна сводка перенумерации очереди; в `queue` ставит «Порядок», из `queue` снимает; в `active` пишет «Взята», в `deferred` дописывает раздел «Отложено» только если его нет, а если раздел уже есть — оставляет файл как есть и печатает «раздел есть, проверь причину и условие возврата»; заголовок «Отложено» внутри fenced-примера разделом не считается; исходящие ссылки файла пересчитывает от старого каталога к новому, входящие переписывает по всему markdown репозитория. Файл, лежащий плоско в `docs/backlog/` (миграция чужого трекера), тоже переезжает — с пересчётом ссылок на выросшую глубину. Задача уже в `queue/` с `--top`/`--after M` — не переезд, а перестановка: меняется только «Порядок» | задачи нет; она в архиве; уже в этом статусе (в `queue/` — без `--top`/`--after`); `--after` не из очереди или на саму себя; номер назван в пакете дважды; `--top`/`--after` при нескольких номерах — место для пакета не определено одним числом |
| `archive <N> [--dry-run] [--range <база>..HEAD]` | `git mv` в `archive/<id>-<slug>/task.md`, перепись исходящих и входящих ссылок по всему markdown репозитория, заготовка `result.md`; файл, лежащий плоско в `docs/backlog/`, тоже находится и переезжает в архив с тем же пересчётом ссылок. Файлы под `<docs>/` и `CHANGELOG.md`, которых коснулся ход задачи, печатаются всегда: выборка идёт по коммитам, чей **заголовок** начинается с `<prefix>-N:` (номер сравнивается числом, тело сообщения не считается — squash тащит туда чужие заголовки), а `--range` добавляет к ней коммиты диапазона. Карточки трекера (`<docs>/backlog`, `<docs>/archive`) из списка исключены; пути — от корня проекта и тогда, когда проект лежит в подкаталоге репозитория: префикс подкаталога команда срезает сама, потому что combined diff merge-коммита флаг `--relative` не учитывает. Merge-коммит добавляет только то, что изменил сам merge, — правку при слиянии (`--cc`); файлы ветки приходят через её коммиты: с `--range` — как часть диапазона, без него — только те, чей заголовок начинается с `<prefix>-N:`. Список — заготовка строки «Доки тем же ходом» для approver'а; в `result.md` команда не вписывает ничего | задачи нет; уже в архиве; каталог занят; `--range` пуст или его ревизия не разбирается — отказ словами git, а не пустой список |
| `adr <slug> [--title "…"]` | `docs/adr/adr-NNN-<slug>.md` из шаблона со следующим номером | плохой slug |
| `brief <N…> [--track "…"] [--neighbour "путь=track"] [--entry "…"] [--autonomy "…"] [--handover "…"] [--measurements]` | печатает в stdout бриф worker'у: заголовок track'а, постановки названных задач с диска (`Что сделать` и `Не входит`), `gates`, `prefix` и `cli` проекта и неизменные разделы из [templates/brief.md](../../templates/brief.md). Решения оркестратора идут текстовыми аргументами: `--neighbour` (повторяется) — границы правки, `--entry` — где лежит предмет и с чего начинать чтение, `--autonomy` — что участник закрывает сам и с чем идёт к оркестратору, `--handover` — протокол гейта и шапка отчёта. Без флага слот печатает `[TODO: …]` — требование к автору брифа, а не умолчание. `--measurements` добавляет правило замера. Шаг гейтов зовёт раннер `gates` только там, где пинованная версия его несёт: команда появилась в v0.5.0, и на пине старее блок перечисляет команды поля `gates` по одной с требованием кода возврата у каждой. Команда только печатает: куда отправить бриф, решает оркестратор | номера задач не названы; задачи нет ни в статусах, ни в архиве (частичный бриф не печатается); `--neighbour` не в форме «путь=track»; задача в архиве без `task.md` — постановки нет |
| `seed --scan [--json]` \| `seed --queue-reference` | `--scan` печатает кандидатов в `gates` (`package.json` scripts, цели `Makefile`/`justfile`/`Taskfile`, шаги `.github/workflows/*.yml` и `.gitlab-ci.yml`, `dotnet build`/`test` по `*.csproj`/`*.sln`, `pytest`/`ruff`/`mypy` по `pyproject.toml`/`setup.cfg`/`tox.ini`) и в подсистемы (`src/*`, `services/*`, `apps/*`, `packages/*`, проекты `.csproj`, точки входа, `bin/*`) — каждый пункт с путём-уликой; отбор остаётся агенту и владельцу. `--queue-reference` читает таблицу `<docs>/reference/README.md` и заводит `describe-<slug>` в очередь на каждую строку, чей файл раздела ещё не написан; slug берётся из имени файла-цели, «Область» заводимой задачи — строка таблицы со ссылкой на индекс справочника (сам раздел ещё не написан), повторный запуск дублей не плодит и считает пропущенные. Выход сборки и окружений (`dist`, `obj`, `.venv`, `vendor`, `target`, `build`) в обход не входит | режим не назван или названы оба; `--json` при `--queue-reference`; нет `reference/README.md` |
| `status [--json]` | сводка по каталогам | — |
| `lint` | гейты трекера, adapters и равенство шаблонов, см. [03](03-lint.md) | найдены ошибки |
| `gates [--keep-going] [--json] [--require-clean] [--dry-run]` | гонит команды из `gates` по порядку, каждую оболочкой; печатает по строке на гейт — команда, исход (свой код возврата, смерть по сигналу или незапуск) и время — и в конце «гейтов N, зелёных M» со снимком дерева (`HEAD` и чистота, если есть git; в репозитории без коммитов `head` — `null`, а строка вывода говорит «коммитов ещё нет»). Без `--keep-going` останавливается на первом красном; `--require-clean` отказывает на грязном дереве до первой команды; `--dry-run` печатает перечень, ничего не исполняя; `--json` отдаёт тот же состав машиночитаемо и уводит вывод самих гейтов в stderr, а вместе с `--dry-run` — `{gates:[{command}], total, dryRun:true}`, без кода и времени: их неоткуда взять. Потолок ожидания на гейт — 10 минут: залипшая команда иначе держала бы прогон вечно | хоть один гейт не вернул ноль — включая смерть по сигналу и незапуск; `gates` пуст; `--require-clean` на грязном дереве или без git; `--dry-run` вместе с `--require-clean` |
| `tracks [--json]` | worktree и локальные ветки захода: путь, ветка, влита ли в `HEAD` (`merge-base --is-ancestor`), коммиты `<prefix>-N` мимо `HEAD` (по заголовку коммита, не по телу: схлопнутый коммит тащит чужие заголовки в тело), незакоммиченное в worktree. Detached worktree меряется по своему sha. Разбор `git worktree list --porcelain` один — `worktrees` в [lib/util.js](../../lib/util.js), им же `new` считает номера чужих worktree. Своё дерево и своя ветка не печатаются; ветка без worktree попадает в перечень, только когда несёт коммиты задач мимо `HEAD`. Команда только наблюдает — удаляют `git worktree remove` и `git branch -D` | git-репозитория нет |
| `upgrade [--to X.Y.Z] [--dry-run] [--pin-only]` | теги `vX.Y.Z` из `source` или из формы `cli`; пробный `<новый cli> version`; пин в `cli` и `gates`, а с ним и упоминания пина в `docs/**` и корневых `*.md` (кроме `CHANGELOG.md`, `docs/adr/**`, архива и карточек задач) — по спеке `cli` с любым номером, поэтому отставшая на две версии проза чинится тоже; число заменённых файлов печатается в момент переписи, а не в плане — предсказание и факт дали бы два числа вместо одного; затем `<новый cli> migrate`, `<новый cli> init`, `<новый cli> changelog --since <старая> --to <новая>` (без `--since`, если старой нет). `--pin-only` сокращает этот хвост и прозу не переписывает — после ручных `migrate` и `init` следующий полный `upgrade` проверит живые файлы и переставит пины даже на том же последнем теге; проба новой версии идёт и с ним | нет ни источника, ни формы `npx github:`; тега `--to` нет в источнике; цель старше 0.2.0 или ниже текущей; ls-remote или пробный запуск отказали — пин не тронут; сбой после пина — отказ называет, чем довести |
| `migrate [--dry-run]` | миграции из списка `MIGRATIONS` для штампа ниже их версии, затем штамп; список пока пуст | штамп новее инструмента |
| `changelog [--since X.Y.Z] [--to X.Y.Z]` | секции CHANGELOG backslop с версией строго после `since` и не позже `to` (по умолчанию — версия инструмента) | версия не по форме |
| `merge-changelog --ours <ref> --theirs <ref> [--base <ref>] [--out <файл>]` | слить две редакции `CHANGELOG.md`, прочитанные `git show <ref>:./CHANGELOG.md`: записи первой секции невыпущенного объединяются по заголовку `- **…**`, жирные подгруппы и их порядок сохраняются, выпущенные секции берутся у `--ours` целиком. Совпавший заголовок с одинаковым телом — одна запись; с разошедшимися телами — обе под меткой `<!-- backslop:conflict …  -->`, выбор за агентом. `--base` снимает запись, которой сторона лишилась относительно базы; **без `--base` односторонняя запись сохраняется, а пометка о ней уходит в отчёт, а не в файл** — снятие от новизны без базы не отличить. Результат — в stdout или в `--out`, отчёт (счёт записей, односторонние, помеченные пары) — всегда в stderr | нет `--ours` или `--theirs`; ревизия не читается; у стороны `--ours` нет секции невыпущенного |
| `version`, `help` | версия из `package.json`; справка — также `--help` у любой команды | — |

Мутационную пробу шаг 4 managed-блока требует только там, где есть чем её гнать: команду берёт поле `probe` в `backslop.json` ([01](01-layout.md)) — непустая однострочная команда без обратной кавычки и без меток `backslop:start`/`backslop:end`: шаблон ставит значение в код-спан, кавычка внутри его закрывает; перевод строки развалил бы блок, а метка оборвала бы его границу, которую `init` ищет по сырому тексту. Поле объявлено — шаг называет команду; поля нет — предложения про пробу в блоке нет вовсе, потому что правило, которое нечем исполнить, дороже отсутствия правила. Выкинутое требование `init` называет строкой вывода («probe в backslop.json не объявлен…»): молчание не отличить от забытого поля. Свою пробу репозиторий без поля описывает разделом вне managed-блока — такой раздел переживает `init` ([ADR-021](../adr/adr-021-probe-command-field.md)).

Текст нумерованных шагов managed-блока `AGENTS.md` можно адаптировать в проекте через `agents.stepOverrides` в `backslop.json`: ключ — строковый номер от `"1"` до `"7"`, значение полностью заменяет текст этого шага при `init`, а номер и остальные шаги сохраняются. Значение должно быть непустой строкой без переводов строк и символа `<`; такой конфиг `init` отклоняет до записи managed-блока. Всё, что проверку прошло, подставляется экранированным: вся ASCII-пунктуация CommonMark уходит под обратную косую, и значение остаётся текстом, а не разметкой — определение ссылки `[label]: /target` в нём не открывается, соседний шаг ссылкой не становится и цель ссылки за пределами блока не меняется. Скобки без определения ссылки остаются законным значением. Список экранируемого полон по построению, а не по перечню: спека объявляет экранируемым любой символ ASCII-пунктуации, а открыть конструкцию markdown нечем, кроме символа из этого класса ([ADR-020](../adr/adr-020-agents-step-overrides.md)). Граница worker'а остаётся под управлением шаблона. Сам блок по-прежнему переписывается из шаблона между маркерами.

Пункт о границах в самом брифе уточняет: approver закрывает задачи и правит текст файлов в каталогах статусов и архиве, а worker присылает формулировку в результате; исключение — новая находка: worker заводит её отдельным файлом через `new --parent N[.M]` в своей ветке, но уже созданные карточки не правит; перенос файлов между этими местами worker не делает.

Даты, которые ставят команды («Создана», «Взята», «Отложена», «Закрыта»), — календарная дата машины по её часовому поясу, не UTC ([lib/util.js](../../lib/util.js), `today`). Файл вне индекса git (или репозитория нет) `mv` и `archive` переносят обычным переименованием и предупреждают. Два файла с одним номером — отказ с обоими путями: молча взять первый значило бы двигать не ту задачу. Место в очереди `mv` считает до переноса, поэтому отказ `--after` файл не трогает; тем же принципом все отказы, видимые до переноса, случаются до первого переноса: половина перенесённого пакета оставила бы каталоги в состоянии, которое ниоткуда не прочитать. Отказ самой файловой операции на середине пакета так не отменяется — атомарна проверка, а не перенос. Порядок каждому номеру считается заново, когда до него дошла очередь, — иначе весь пакет получил бы один «Порядок». Файлы задач читаются без BOM, переводы строк сохраняются какими были. Длинный вывод (`status --json`) доезжает до читателя целиком: код возврата ставится через `exitCode`, закрытый читателем пайп — тихий выход.

`upgrade` обновляет только вверх: пин и штамп на последнем теге — «уже на vX», цель ниже текущей — отказ, как и цель старше 0.2.0 (у неё нет `migrate`). `--to` нужен, чтобы выбрать не последний тег или повторить обновление на ту же версию после сбоя. Формы `cli` с пином — `npx [флаги] github:owner/repo[#vX.Y.Z]` и `npx [флаги] backslop@X.Y.Z`; флаги npx сохраняются. `npx backslop` и `npx backslop@latest` — та же npm-форма с `pin: null`: `lint` предупреждает, `upgrade` пина не выведет из registry. GitHub-форма даёт источник тегов; npm-форма — нет, и без поля `source` `upgrade` отказывает. `cli` не в этих формах (глобальная установка, репозиторий инструмента) — пин не трогается, команды новой версии запускаются тем же `cli`; без поля `source` в этом случае — отказ. Всё, что зависит от формата, делает новая версия: `upgrade` может идти из старой. Команды новой версии исполняются оболочкой из строки `cli` как есть — тот же уровень доверия к `backslop.json`, что у `gates`. `init` и `migrate` отказывают, когда штамп новее их самих: понижение версии не поддерживается.

`upgrade` переписывает пин в `backslop.json`, поле `gates` и живых файлах: markdown из `docs/**` и корневые `*.md` с историческими исключениями, каждый файл с именем `package.json` и известные CI-файлы. Старый пин в живом файле — ошибка `lint`; исторические записи остаются зелёными. `--pin-only` меняет только конфигурацию и гейты; после ручных `migrate` и `init` повторный полный `upgrade` чинит живые пины, даже если новый тег не появился.

Бамп версии — отдельный ход до релиза: `npm run release -- X.Y.Z --bump` пишет `version` в `package.json`, переименовывает верхнюю секцию `CHANGELOG.md` в `## vX.Y.Z — <дата>` и ставит штамп `backslop.json` вызовом `init`; все проверки идут до первой записи, коммитов скрипт не делает — дифф смотрит и коммитит агент. Рассинхрон этих трёх чисел ловит одиннадцатый гейт `lint` ([03](03-lint.md)).

Релиз самого пакета — `npm run release -- X.Y.Z` ([scripts/release.mjs](../../scripts/release.mjs)): чистое дерево на `main`, совпадение версии и тега, `git fetch` и fast-forward от `origin/main` (локальный `main` может быть впереди), `npm test`, `lint`, `pack --dry-run`, локальный тег, `git push --atomic --dry-run`, затем `npm publish` и atomic push `main` и тега. `--no-publish` снимает только шаг `npm publish` — тег и atomic push остаются: пока публикация отложена владельцем ([BS-2.1](../backlog/deferred/BS-2.1-npm-publish.md)), это и есть штатный релизный путь, и отчёт скрипта в этом случае говорит «npm publish не запускался». `--bump` и `--no-publish` вместе — отказ: бамп до релиза не доходит и ничего не публикует. Рабочие копии субагентов `.claude/worktrees/` игнорируются и чистоту release-preflight не нарушают. Acceptance-тест ([test/release.test.mjs](../../test/release.test.mjs)) собирает tarball настоящим `npm pack` и сверяет его состав с полем `files`: каждый отслеживаемый git файл под `bin`, `lib`, `templates` и корневые `README.md`, `README.ru.md`, `LICENSE`, `CHANGELOG.md` упакован, сверх них — только `package.json`. Сбой после тега печатает состояние и следующую команду. Default `cli` до первой публикации остаётся GitHub-формой ([ADR-007](../adr/adr-007-npm-pin.md)).

Порядок при постановке в очередь ([lib/tasks.js](../../lib/tasks.js), `placeInQueue`): в конец — максимум плюс 10; `--top` — середина между нулём и первым; `--after M` — середина между M и следующей. Целого места нет — вся очередь перенумеровывается шагом 10 с сохранением порядка, команда об этом сообщает. Перестановка задачи, уже стоящей в очереди, считается так же, только без неё самой среди соседей; файл остаётся на месте, ссылки не переписываются.

## `status --json`

```json
{
  "prefix": "BS",
  "docs": "docs",
  "active":   [{ "id": "BS-2", "title": "…", "file": "docs/backlog/active/BS-2-x.md", "created": "2026-09-03", "taken": "2026-09-04" }],
  "queue":    [{ "id": "BS-1", "title": "…", "file": "docs/backlog/queue/BS-1-y.md", "created": "2026-09-03", "order": 10 }],
  "deferred": [{ "id": "BS-3", "title": "…", "file": "docs/backlog/deferred/BS-3-z.md", "created": "2026-09-01", "deferred": "- **Отложена:** 2026-09-02" }],
  "triage":   [{ "id": "BS-2.1", "title": "…", "file": "docs/backlog/triage/BS-2.1-w.md", "created": "2026-09-04" }],
  "archive": 12
}
```

Очередь отсортирована по порядку, затем по номеру; задача без порядка идёт в конец с `order: null`. `deferred` — первая непустая строка раздела «Отложено». Пути — от корня проекта в posix-форме.

## Что стабильно

Оркестратор любого harness работает с backslop через файлы и CLI; другого API нет. Стабильное:

- каталоги статусов и архив; имя файла `<prefix>-N[.k]-<slug>.md`; русские и английские поля шапки и разделы задачи, включая совместимые `Scope`/`Area`;
- поля `backslop.json`: `prefix`, `docs`, `cli`, `gates`, `probe`, `version`, `source`, `lang`, `tools`; формы пина `npx github:owner/repo#vX.Y.Z` и `npx backslop@X.Y.Z`;
- команды `status --json`, `mv`, `new --parent N[.M]`, `archive` и их коды возврата — ими оркестратор читает очередь, раздаёт и закрывает задачи;
- worker командами статусов не пользуется: его единственная запись — файл находки `new <slug> --parent N[.M]` в своей ветке; при `--parent N.M` `new` выдаёт следующий свободный `N.k` и записывает поле `Parent`; команда видит номера соседних worktree и локальных веток;
- транспорт worker'ов — слот «Как поднять worker'а» в скилле `backslop-batch`; новый транспорт — страница с вариантом для этого слота, в CLI ничего не меняется.

Изменение любого пункта — новым ADR.
