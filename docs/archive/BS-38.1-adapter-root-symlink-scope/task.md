# BS-38.1 · Symlink на корне harness: легитимен ли realpath внутри корня и нужна ли проверка корня adapter'а вне tools

- **Область:** `lib/adapters.js`, `lib/init.js`, [01-layout](../../reference/01-layout.md)
- **Создана:** 2026-09-09
- **Зависимости:** нет
- **Взята:** 2026-09-09

## Контекст

Открытый вопрос вынесен из BS-38 её же разделом «Что сделать» («Отдельным открытым вопросом (не решать в этой задаче) — владельцу») и «Не входит» («Сам ответ… — решение владельца, не код этой задачи»). BS-38 переставила проверку корней harness до первой записи и объяснила отказ, но объём проверки оставила прежним.

Сегодня `ownedPath` (`lib/adapters.js`) бракует symlink на любой компоненте пути под корнем проекта, не глядя на `realpath`, а `checkAdapterRoots` зовёт её на всех трёх корнях независимо от `cfg.tools`. Улика — проба на HEAD 1b1f226 (воспроизведена, вывод дословно): в проекте с `ln -s ../shared-claude .claude` команды `init --tools claude`, `init` и `init --tools none` дают `✖ adapter path содержит symlink: .claude`, код 1 у каждой. Тест `init: symlink на корне harness — отказ до записи конфига, любые --tools` (`test/init.test.mjs`) фиксирует именно это поведение и сознательно берёт цель symlink вне корня проекта, чтобы не предрешать вопрос ниже.

Следствие: проект, у которого harness-каталог — общая ссылка (одна на несколько рабочих копий), не проходит `init` никогда, даже с `tools: []`, где backslop в этот каталог не пишет ни одного файла.

## Что сделать

- Решение владельца по двум развилкам, дальше — код по решению:
  - считать ли owned-путём symlink, чей `realpath` лежит внутри корня проекта (сейчас — нет; риск записи и unlink сквозь чужую ссылку тогда снимается сравнением `realpath`);
  - звать ли `ownedPath`/`markedFiles` на корне adapter'а, которого нет в `cfg.tools` и под которым нет ни одного файла с маркером (сейчас — да, и это единственная причина отказа при `tools: []`).
- Смена ответа на любую из развилок меняет контракт `init` (условие отказа) — тогда ADR, а не правка кода.

## Не входит

- Расширение проверки на другие каталоги проекта: предмет — только три корня harness.
- Отмена самой охраны symlink внутри `write`/`removeFile` — она стоит по ADR-006 и работает как задумано.

## Проверки

- Проба «symlink на `.claude`, цель внутри корня проекта» ведёт себя так, как решил владелец, и это зафиксировано тестом.
- `node bin/backslop.js lint` и `npm test` зелёные.


## Решение владельца (2026-09-09)

Из двух развилок принята одна: `init` проверяет на symlink только корни adapter'ов, выбранных в `cfg.tools`; корни невыбранных не проверяются, потому что backslop туда не пишет и ничего не снимает. Ссылка, ведущая наружу из проекта, на выбранном корне остаётся отказом; ссылка внутрь проекта отдельно не разрешается — вторая развилка отклонена. Это смена условия отказа `init`, то есть контракта: реализация идёт с ADR, который заменяет соответствующую часть BS-38 и уточняет ADR-006.
