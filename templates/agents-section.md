## Задачи и решения — backslop

Трекер задач и журнал решений живут в `{{docs}}/` и ведутся командой `{{cli}}` (конфиг — `backslop.json`, префикс задач — `{{prefix}}`). Списка задач в файлах нет: работу, очередь, отложенное, triage и minor по областям печатает `{{cli}} status`. Правила ведения — `{{docs}}/backlog/README.md`, кто что решает — `{{docs}}/ROLES.md`, термины — `{{docs}}/GLOSSARY.md`. Версия раскладки — поле `version` в `backslop.json`; обновление backslop — `{{cli}} upgrade`, по своему решению, а не по чужому коммиту.

**Скиллы (если выбран adapter):** `backslop-task` — цикл одной задачи; `backslop-batch` — заход worker'ами по track'ам; `backslop-seed` — наполнение документации после установки; `backslop-writer`, `backslop-techdoc` и `backslop-humanizer` — проход по актуальности и стилю документации и правила письма, которые он применяет.

Если выбран adapter, перед релизным коммитом запусти проход `backslop-writer` в режиме release по диффу от предыдущего тега.{{hooksRule}}

**Процедура изменения.** Роли две: worker правит и проверяет (шаги 1–4), approver принимает и закрывает (5–7); одиночный агент совмещает обе и идёт по шагам подряд.

1. **Задача.** Возьми первую в очереди (`{{cli}} status`) или заведи: `{{cli}} new <slug> --title "…"` — в triage, с `--queue` — сразу в очередь. Мелочь без следа в трекере допустима, если правка исчерпывается одним заходом и не меняет контракт. Находка идёт с меткой цены: `critical` чини сейчас, `major` в области текущей задачи чини сейчас, `major` вне её — файл `{{cli}} new <slug> --parent N[.M]`, затем допиши строку `Улика:` его «Контекста»; `minor` — `{{cli}} new <slug> --parent N[.M] --minor --evidence "…"`; без улики команда отказывает. Гипотеза о `major` или `critical` заводится так: `{{cli}} new <slug> --parent N[.M] --minor --cost <уровень> --hypothesis --evidence "…"`; голый `--minor --evidence` — только для minor-находки.
2. **Правка.** Реверс прежнего решения — чистым удалением, без зачёркиваний и пометок «отменено». Стиль существующего файла сохраняй. Термины — из глоссария; нужного нет — предложи владельцу, молча не выдумывай.
3. **Доки тем же ходом.** Незадокументированное изменение считается незавершённым: справочник `{{docs}}/reference/`, README затронутой подсистемы, CHANGELOG. Архитектурное решение — `{{cli}} adr <slug>` и строка в таблицу `{{docs}}/README.md`; новое решение по уже решённому вопросу переписывает этот ADR. Правка документации несёт проверку, которая краснеет на старом тексте: блок `quote:`, тест или правило lint. Документация не ссылается на задачи: излагай контракт, обоснование или замер.
4. **Гейты до отчёта.** `{{cli}} gates` зелёный: команды из `gates` в `backslop.json`, код каждой и счёт «гейтов N, зелёных M». Запись с областью `when` на нетронутых путях пропускается: пропущенное идёт отдельным числом «не запущено N», к зелёным не прибавляется и называется в отчёте отдельной строкой. Закоммить в свою ветку с префиксом `{{prefix}}-N:` до отчёта; незакоммиченного не остаётся. Для закоммиченной ветки вызов — `{{cli}} gates --require-clean --base <база>`, где `<база>` — коммит до взятия задачи: без `--base` считаются только незакоммиченные пути, и гейты с областью пропускаются.{{probeRule}}
5. **Приёмка и архив** — approver'ом, одним ходом: ревью диффа, `{{cli}} archive N`, дописать `result.md` (исход, что сделано, чем проверено), `{{cli}} fold N > "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` — каталог сворачивается в строку `{{docs}}/archive/LOG.md`, а тело задачи уезжает в заготовку сообщения коммита, которая ложится вне рабочего дерева. Между `archive N` и `fold N` не коммить: такой коммит станет ревизией строки журнала, и squash унесёт её из истории. Итоговый коммит приёмки несёт заготовку сообщением: `git add -A`, `git reset --soft <база>`, `git commit --cleanup=verbatim -F "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` — тело оставь; `fixup` поверх коммита worker'а заготовку выбрасывает. **Ветка с вложениями:** `fold` отказывает, пока вложение из каталога задачи не окажется в `HEAD`, поэтому сначала склей коммиты вместе с каталогом: `git add -A`, `git reset --soft <база>`, `git commit -m "{{prefix}}-N: <что сделано>"`; затем `{{cli}} fold N > "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"` и закоммить результат: `git add -A`, `git commit --cleanup=verbatim -F "$(git rev-parse --git-dir)/BACKSLOP_DRAFT"`. Строка журнала называет склеенный коммит, который хранит каталог с вложениями; задача попадает в основную ветку этими двумя коммитами, и после свёртки ничего не склеивается. На Windows выполняй эту последовательность команд в Git Bash.
6. **Разбор triage** — сразу после закрытия; он закончен, когда у каждой записи, оставшейся в `triage/`, есть названный ход: слита, переехала в другой каталог или закрыта решением владельца (`{{docs}}/backlog/README.md`, раздел «Такт разбора triage»). Ход — например, слияние в другую задачу, уточнённая формулировка, `{{cli}} mv N queue` или `{{cli}} mv N deferred` с условием возврата. К владельцу — только за отказом.
7. **Фиксация.** Коммит с номером задачи первым в сообщении: `{{prefix}}-N: <что сделано>`. В основную ветку задача уезжает одним коммитом, а в ветке с вложениями из шага 5 — двумя: правки по ревью схлопываются в коммит приёмки из шага 5, и взятие тоже, когда им взята одна эта задача и `git rev-list <take>..HEAD` ничего не печатает: `reset --soft` шага 5 идёт на `<take>^`. Иначе коммит взятия остаётся отдельным коммитом, и коммит приёмки об этом говорит: приёмка одной задачи никогда не поглощает взятие другой, а `reset --soft` идёт на `<head>` — голову main непосредственно перед текущим слиянием, — но не на коммит взятия нескольких задач: он заменил бы стоящие выше ранние приёмки и потерял бы их заготовки. После него правки разбора triage из шага 6 идут отдельным коммитом с subject `{{prefix}}: triage after {{prefix}}-N`: в коммите задачи N чужих переносов статусов быть не должно. После свёртки squash не делается — он выбросил бы заготовку, единственное хранилище тела задачи. `{{cli}} lint` зелёный на итоговом коммите; затем пуш.

Границы worker'а: правит только свою ветку или worktree; новые файлы находок создаёт только командой `{{cli}} new`; существующие файлы задач не правит, не переносит и не архивирует (ни `mv`, ни `archive`); `{{docs}}/archive/` не трогает; закрытие и triage — approver.

**Разговор с владельцем.** Сообщение владельцу — вопрос, статус, отчёт о заходе — читается без открытой очереди, захода и твоего контекста. На вопрос отвечают по его собственному тексту: в нём сказано, что спрашивается, зачем и что меняет каждый ответ, — владелец решает, а не нажимает рекомендованный вариант. Не используй термины и сокращения, которые ты ввёл сам (slug worker'а, «кусок», код замечания вроде F1); определение, новое для владельца, берётся в речь только после его подтверждения. Задачу называй номером и заголовком, `{{prefix}}-N — <заголовок>`, не одним номером: заголовок стоит при первом упоминании в сообщении, в каждом заголовке раздела и в каждой строке таблицы; дальше в том же абзаце можно называть одним номером; каждый пункт списка — отдельный абзац.
